Identity, Key Vault & Bicep Scaffold

Capstone Track 1 — Weeks 1–3

🔨 CAPSTONE ⏱ ~90 min 💳 Est. cost: <$1 per session 🧱 Bicep + Azure CLI
What you'll build: The identity and secrets foundation of the SecureAI API. By the end of this session you will have deployed an App Service with a system-assigned managed identity that reads a secret from Key Vault — without a single hardcoded credential — all provisioned from Bicep and torn down cleanly when you're done.

1. Track 1 Architecture

Track 1 establishes the identity backbone. Every resource deployed here is reused and hardened in later tracks. The key security pattern is: Managed Identity → RBAC → Key Vault. No passwords. No connection strings in code.

sequenceDiagram participant DEV as 👤 You (PIM JIT) participant BICEP as Bicep Deployment participant ENTRA as Entra ID participant APP as App Service participant KV as Key Vault DEV->>ENTRA: Activate PIM role (JIT, 1hr) ENTRA-->>DEV: Contributor role active DEV->>BICEP: az deployment group create BICEP->>APP: Deploy App Service + enable System MI BICEP->>ENTRA: Entra registers System MI automatically BICEP->>KV: Deploy Key Vault (RBAC mode, firewall on) BICEP->>ENTRA: Assign KV Secrets User role → MI Note over APP,KV: ✅ No credentials in code — MI auth only APP->>ENTRA: Request token for vault.azure.net ENTRA-->>APP: Bearer token (short-lived) APP->>KV: GET /secrets/db-password (Bearer token) KV-->>APP: Secret value ✅ DEV->>BICEP: az group delete (destroy)

4. main.bicep — The Orchestrator

main.bicep is the entry point. It declares parameters, names resources consistently, and calls each module. The modules do the actual resource deployment. 

// main.bicep — SecureAI API: Track 1 scaffold
// Deploy: az deployment group create --resource-group rg-secureai-dev --template-file main.bicep --parameters @params.json adminPublicIp=$myIp

@description('Environment suffix for resource naming (dev | staging | prod)')
param environment string = 'dev'

@description('Azure region for all resources')
param location string = resourceGroup().location

@description('Your public IP — granted Key Vault firewall access for admin work')
param adminPublicIp string

var appName = 'secureai-${environment}'
var kvName  = 'kv-secureai-${environment}'

// ── Modules ────────────────────────────────────────────────────────────────

module appService 'modules/app-service.bicep' = {
  name: 'appServiceDeploy'
  params: { appName: appName, location: location }
}

module keyVault 'modules/key-vault.bicep' = {
  name: 'keyVaultDeploy'
  params: { kvName: kvName, location: location, adminPublicIp: adminPublicIp }
}

module rbac 'modules/rbac.bicep' = {
  name: 'rbacDeploy'
  params: {
    kvName: kvName
    appServicePrincipalId: appService.outputs.principalId
  }
  dependsOn: [keyVault]    // KV must exist before role assignment
}

module policy 'modules/policy.bicep' = {
  name: 'policyDeploy'
  params: { resourceGroupName: resourceGroup().name }
}

// ── Outputs ─────────────────────────────────────────────────────────────────

output appServiceName     string = appService.outputs.appServiceName
output keyVaultUri        string = keyVault.outputs.keyVaultUri
output appManagedIdentity string = appService.outputs.principalId
Security point — dependsOn: The RBAC module explicitly depends on the Key Vault module. Without this, Bicep may attempt the role assignment before the vault exists, causing a deployment failure. Explicit dependencies make execution order predictable and auditable — the same principle applies to policy assignments and role definitions in large IaC repos.

5. modules/app-service.bicep

Creates an App Service Plan (Linux B1) and an App Service site. The critical security line is identity: { type: 'SystemAssigned' } — this is what tells Azure to create a managed identity for this app automatically. 

// modules/app-service.bicep
param appName string
param location string

resource appServicePlan 'Microsoft.Web/serverfarms@2023-01-01' = {
  name: 'asp-${appName}'
  location: location
  sku: { name: 'B1', tier: 'Basic' }
  kind: 'linux'
  properties: { reserved: true }
}

resource appService 'Microsoft.Web/sites@2023-01-01' = {
  name: appName
  location: location
  identity: {
    type: 'SystemAssigned'    // ← the managed identity declaration
  }
  properties: {
    serverFarmId: appServicePlan.id
    httpsOnly: true              // ← enforce TLS — plain HTTP is rejected
    siteConfig: {
      linuxFxVersion: 'PYTHON|3.12'
      minTlsVersion: '1.2'        // ← TLS 1.0/1.1 disabled
      ftpsState: 'Disabled'       // ← FTP credentials attack surface removed
    }
  }
}

output appServiceName string = appService.name
output principalId    string = appService.identity.principalId
Why httpsOnly: true and ftpsState: 'Disabled' matter: These are two of the most-flagged issues in Defender for Cloud's App Service recommendations. Setting them in Bicep means they are enforced by infrastructure, not reliant on portal configuration that could drift. The Azure Policy module (Step 8) will also enforce HTTPS at policy scope.

6. modules/key-vault.bicep

Creates a Key Vault with RBAC-based access control (not legacy access policies), soft-delete, purge protection, and a network firewall that denies all traffic by default except from your public IP. 

// modules/key-vault.bicep
param kvName         string
param location       string
param adminPublicIp  string

resource keyVault 'Microsoft.KeyVault/vaults@2023-07-01' = {
  name: kvName
  location: location
  properties: {
    sku: { family: 'A', name: 'standard' }
    tenantId: tenant().tenantId
    enableRbacAuthorization: true     // ← RBAC mode; access policies are disabled
    enableSoftDelete: true
    softDeleteRetentionInDays: 7      // ← minimum for dev; use 90 in production
    enablePurgeProtection: true       // ← once set, cannot be disabled without waiting
    networkAcls: {
      defaultAction: 'Deny'           // ← deny all traffic by default
      bypass: 'AzureServices'         // ← allow trusted Azure services (Defender, etc.)
      ipRules: [
        { value: '${adminPublicIp}/32' }  // ← your IP only (portal + CLI access)
      ]
    }
  }
}

output keyVaultUri string = keyVault.properties.vaultUri
output keyVaultId  string = keyVault.id
Purge protection caveat: Once enablePurgeProtection: true is set on a vault, it cannot be turned off and the vault cannot be immediately purged after deletion — it must wait out the soft-delete retention window. This is intentional (ransomware protection), but it means if you redeploy with the same kvName before the retention period expires, the deployment will fail. Use a unique name suffix or wait 7 days. For speed in dev, you can omit purge protection — but leave it enabled in any environment that matters.

7. modules/rbac.bicep

Grants the App Service's managed identity the Key Vault Secrets User built-in role scoped to the Key Vault resource. This is the minimum permission needed to read secrets — the MI cannot create, update, or delete secrets. 

// modules/rbac.bicep
param kvName                  string
param appServicePrincipalId    string

// Built-in role: Key Vault Secrets User
// https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide
var kvSecretsUserRoleId = '4633458b-17de-408a-b874-0445c86b69e6'

resource keyVault 'Microsoft.KeyVault/vaults@2023-07-01' existing = {
  name: kvName
}

resource miSecretsUser 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  name: guid(keyVault.id, appServicePrincipalId, kvSecretsUserRoleId)
  scope: keyVault
  properties: {
    roleDefinitionId: subscriptionResourceId(
      'Microsoft.Authorization/roleDefinitions',
      kvSecretsUserRoleId
    )
    principalId:   appServicePrincipalId
    principalType: 'ServicePrincipal'
  }
}
Why guid() for the role assignment name? Role assignment names must be GUIDs and must be idempotent — the same assignment on the same resource must produce the same GUID, otherwise re-running the deployment creates a duplicate. Using guid(resourceId, principalId, roleId) as a deterministic hash guarantees idempotency. This is a Bicep best practice for all role assignments.

8. modules/policy.bicep

Assigns a built-in Azure Policy to the resource group that enforces HTTPS-only on App Service. Even though we set httpsOnly: true in the Bicep, this policy provides a governance guardrail — it will flag (and optionally block) any App Service that tries to drift from that setting. 

// modules/policy.bicep
param resourceGroupName string

// Built-in policy: App Service apps should only be accessible over HTTPS
// Definition ID: a4af4a39-4135-47fb-b175-47fbdf85311d
var httpsOnlyPolicyId = '/providers/Microsoft.Authorization/policyDefinitions/a4af4a39-4135-47fb-b175-47fbdf85311d'

resource httpsPolicy 'Microsoft.Authorization/policyAssignments@2022-06-01' = {
  name: 'enforce-https-${resourceGroupName}'
  properties: {
    displayName: 'Enforce HTTPS only on App Service'
    policyDefinitionId: httpsOnlyPolicyId
    enforcementMode: 'Default'     // 'Default' = enforce | 'DoNotEnforce' = audit only
  }
}

10. Deploy

Save this as scripts/deploy.ps1 and run it from the project root:

# scripts/deploy.ps1
param(
  [string]$ResourceGroupName = "rg-secureai-dev",
  [string]$Location          = "eastus",
  [switch]$Destroy
)

if ($Destroy) {
  Write-Host "🗑️  Destroying $ResourceGroupName ..."
  az group delete --name $ResourceGroupName --yes --no-wait
  Write-Host "Deletion queued. Resources are removed within a few minutes."
  exit 0
}

# Fetch your current public IP for Key Vault firewall
$myIp = (Invoke-WebRequest -Uri "https://api.ipify.org" -UseBasicParsing).Content.Trim()
Write-Host "Your public IP: $myIp"

# Ensure resource group exists
az group create --name $ResourceGroupName --location $Location --output none

# Deploy
az deployment group create `
  --resource-group $ResourceGroupName `
  --template-file main.bicep `
  --parameters "@params.json" adminPublicIp=$myIp `
  --output table

Write-Host ""
Write-Host "✅ Deployment complete."
Write-Host "   Run: .\scripts\verify-identity.ps1 -ResourceGroupName $ResourceGroupName"
Write-Host "   Destroy when done: .\scripts\deploy.ps1 -Destroy"
▶
Run the deployment
Set-Location "C:\Projects\secureai-api"
.\scripts\deploy.ps1

The deployment takes 2–4 minutes. Watch for Succeeded in the output table. Note the appServiceName, keyVaultUri, and appManagedIdentity outputs — you'll use them in the verification step.

11. Verify — Managed Identity Reads a Secret

Before moving on, confirm the security controls actually work. Save this as scripts/verify-identity.ps1: 

# scripts/verify-identity.ps1
param(
  [string]$ResourceGroupName = "rg-secureai-dev"
)

$kvName  = az keyvault list --resource-group $ResourceGroupName --query "[0].name" -o tsv
$appName = az webapp list  --resource-group $ResourceGroupName --query "[0].name" -o tsv

# 1. Store a test secret via CLI (your IP is in the KV firewall)
az keyvault secret set --vault-name $kvName --name "test-secret" --value "hello-from-managed-identity"
Write-Host "✅ Secret stored in $kvName"

# 2. Open the App Service SSH console (via portal) and run this to test MI token acquisition
Write-Host ""
Write-Host "To verify the managed identity end-to-end, open the App Service SSH console in the Azure portal:"
Write-Host "  https://portal.azure.com → App Services → $appName → SSH"
Write-Host ""
Write-Host "Then paste this into the SSH shell:"
Write-Host "  TOKEN=\$(curl -s 'http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://vault.azure.net' -H 'Metadata: true' | python3 -c 'import sys,json; print(json.load(sys.stdin)[\"access_token\"])')"
Write-Host "  curl -s \"https://$kvName.vault.azure.net/secrets/test-secret?api-version=7.4\" -H \"Authorization: Bearer \$TOKEN\""
Write-Host ""
Write-Host "Expected: {\"value\":\"hello-from-managed-identity\", ...}"
What success looks like: The curl command in the App Service SSH console returns "value":"hello-from-managed-identity" with no credentials anywhere in the call. The managed identity obtained a short-lived token from Entra ID (via the instance metadata endpoint at 169.254.169.254) and Key Vault accepted it because the MI has the Key Vault Secrets User RBAC role. This is the zero-credential pattern you'll use for all subsequent tracks.

12. Authenticate the Deployment Identity — No Owner, No Windows Hello

Before configuring PIM, get the baseline right: how you sign in and what role you deploy with. Two least-privilege habits matter here — never develop as Owner, and sign in without relying on the Windows Hello passkey prompt so the CLI flow is repeatable and scriptable.

Sign in without Windows Hello

Interactive az login opens a browser that may force a Windows Hello passkey. Use device-code flow to sign in with username/password instead — useful when the target account differs from your Windows session account: 

az login --use-device-code
az account show --query "{name:name, id:id}" -o table

Don't deploy as Owner

Owner grants Microsoft.Authorization/* — the right to hand out access — which IaC almost never needs. Deploy as Contributor scoped to the dev resource group. Only the rbac.bicep role-assignment step needs more, so pair it with User Access Administrator on that RG — never fall back to Owner.

RoleGrantsUse for this capstone
ContributorCreate/manage resources, no access-grantingApp Service, Key Vault, SQL deploys
User Access AdministratorAssign roles, no resource mgmtThe rbac.bicep module only
OwnerBoth of the aboveAvoid — over-privileged for IaC
 
# Contributor + ability to assign RBAC, scoped to the dev RG only
az role assignment create --assignee <you> --role Contributor --scope /subscriptions/<sub>/resourceGroups/rg-secureai-dev
az role assignment create --assignee <you> --role "User Access Administrator" --scope /subscriptions/<sub>/resourceGroups/rg-secureai-dev
Why scope to the RG, not the subscription: the entire capstone lives in one resource group and is destroyed each session. A subscription-wide grant outlives the resources and breaks least privilege. Verify with az role assignment list --assignee $me --all -o table — confirm Contributor, not Owner.

13. Configure PIM for Your Deployment Identity

Now elevate that Contributor role just-in-time. The az deployment group create command runs under your personal account — instead of a permanent Contributor role, make it PIM-eligible. Track 1 theory (Lesson 0002) teaches PIM; here's where you apply it.

  1. Go to Microsoft Entra ID → Privileged Identity Management → Azure resources.
  2. Find your subscription and click Roles → Contributor.
  3. Click Add assignments → Eligible and add your account.
  4. Remove any existing active Contributor assignment on your account at subscription scope.
  5. Next time you need to deploy: activate the Contributor role in PIM (JIT, 1-hour window), then run deploy.ps1.
Keep at minimum one Owner assignment (ideally a break-glass account) to avoid locking yourself out if PIM is misconfigured. Do not remove all active privileged assignments before confirming PIM activation works.

14. Destroy

When you're done with the session, tear everything down. The Bicep files are your persistent artefact — the Azure resources are ephemeral. 

.\scripts\deploy.ps1 -Destroy

Verify deletion: wait 2–3 minutes, then run az group show --name rg-secureai-dev. It should return an error: ResourceGroupNotFound. Check the Azure portal cost dashboard to confirm no unexpected charges.

Key Vault soft-delete: Even after deleting the resource group, the Key Vault enters a soft-deleted state and is retained for 7 days. If you redeploy with the same kvName within that window, the deployment will fail with a name conflict. Either use a unique name (append a date suffix) or purge the deleted vault first: az keyvault purge --name kv-secureai-dev. Note: purge protection on the vault must NOT be set to true if you want to purge immediately — see Step 6.

16. Track 1 Security Controls Checklist

Verify each control is in place before moving to Track 2:

  • App Service deployed with system-assigned managed identity (no credentials in code)
  • App Service enforces HTTPS-only and TLS 1.2 minimum
  • App Service has FTP disabled
  • Key Vault uses RBAC authorisation (not legacy access policies)
  • Key Vault has soft-delete enabled
  • Key Vault has purge protection enabled
  • Key Vault firewall defaults to Deny; only your IP is allowed
  • Managed identity has Key Vault Secrets User role only (least privilege)
  • You deploy as Contributor (not Owner), scoped to the dev resource group
  • CLI sign-in uses device-code flow (no Windows Hello dependency)
  • Azure Policy enforcing HTTPS on App Service assigned to resource group
  • Your deployment identity configured as PIM-eligible (JIT only)
  • Resources destroyed after session; cost dashboard confirmed clear
